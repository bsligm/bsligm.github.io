家里的 Agent 运维试验

发表于2026-10-08|更新于2026-11-23|系统运维基础设施
|总字数:1.6k|阅读时长:4分钟|浏览量:

推理进程停了以后，负责拉起它的计划任务一直在等。那次我手工启动了监督进程，模型重新加载，大约 40 秒后健康检查恢复。GPU 当时为什么异常，还没查清。

如果再来一次，我想让 Agent 先查进程和计划任务，拿到结果后我再决定要不要重启。现有的监控和查询都能单独用，告警自动派调查还在做。

推理池掉线以后，哪些事能交给 Agent

最先要弄清两个时间点：进程何时退出，计划任务应该何时拉它起来。模型重新加载以后也得再问一次。健康检查已经恢复，原记录还缺一条实际推理请求的结果。

下表左边是我当时做的事，右边是准备让 Agent 接手时要看的结果。

阶段 这次怎么处理 接入 Agent 后怎么验
观测 发现健康检查失败 关联告警时间、实例身份和探活结果
调查 核对监督任务和推理进程状态 用只读证据区分进程退出、模型冷启动和服务不可达
审批 人工决定是否恢复监督任务 提交目标、影响和停止条件，获准后执行
回读 等待模型加载并再次检查健康状态 查进程与端点，再发一条实际推理请求确认业务
归档 记录恢复动作与待查根因 保存结果及适用范围，供下一次调查核对

Agent-first OS：先把执行入口做稳

Windows 接入里，我把标准输出、错误输出和退出码分开留存，失败时可以识别是远程执行没起来，还是命令执行后返回了错误。Web 服务优先用产品本身提供的 API。每条入口都要能识别调用者、约束权限、留下可回读的结果。涉及权限或生产配置的变更，由人确认目标和影响范围。

用推理池做例子，健康端点、进程状态和监督任务状态来自不同接口。Agent 至少应返回查询对象、数据来源、时间和结果。查不到实例与明确读到实例已停止，需要两个不同的状态，避免把网络波动误判成服务退出。

数据写入即语义化：把证据的范围一起存下来

任务记录至少写任务 ID、场景、阶段、时间和验证状态。比如推理服务恢复后，健康检查成功、模型能回答一条真实请求、硬件故障已经排除，是三件不同的事。字段里写清实际做到哪一步。详细日志留在原来的系统，知识库引用必要的证据和当时的判断。

回头看第一次恢复，健康检查转绿很容易让人把故障单关掉。但这条记录还有两格空着：业务请求有没有恢复的原始证据，以及进程当时为什么退出。两格分别影响当前可用性判断与以后能不能按同一规程处理。接手的新 Agent 应先报告这两处缺口，再用当前状态补证据。

事件驱动 Agent Swarm：从通知走到调查

监控已经能发现异常并通知人，目前仍由人发起调查。下一步可以让告警携带对象和时间窗，自动启动只读检查。监控负责报异常，调查任务收集证据，复核任务核对归因。涉及重启和访问权限调整的动作保留审批。自动唤醒和多任务协作仍需完整演练。

有两个用例还得试。同一实例的告警连续发两次，应该只开一份调查。模型正在加载时探活失败，调查里应该先有进程和加载状态。恢复请求发出去以后也得先查实际状态，免得多拉一个实例。

计划中的执行接口还需要一次失败演练：操作已经发出，但调用方等不到响应。调查应读回服务和监督任务的实际状态。如果发现模型正在加载，就记录观察窗口，保留原审批上下文。如果连状态也读不到，停在待核实，把最后一次操作的时间和目标交给人。这一条决定了流程能不能从中断安全接回来。

知识自动回流：下次从上次的判断接着查

同类故障再次出现，Agent 会先查已有记录，匹配适用范围，再核对当前版本和现场状态。推理池那次我记了两件事：手工恢复后健康检查重新通过，底层资源异常的根因仍待定位。第二次查到这条记录，可以少翻一轮日志，又不会把临时恢复写成永久修复。记录写入和下次检索分别验收，只有能稳定找到并正确使用的记录才算形成反馈。

这条经验归档时适用范围应写成“监督任务未运行、推理进程退出未拉起”。如果新告警中进程还活着，或能确认模型正在加载，旧记录只能提供检查顺序。能否拒绝给一个相似告警套用旧动作，是检索验收里最有用的反例。

自然语言操作面：一句话续跑，权限照旧

已有任务最适合测试这条路径。用户说“继续”，Agent 能从任务记录、代码版本和上次验证结果确定从哪一步接手。如果遇到多个同名目标或新的授权边界，先核对再动手。查状态、准备修改和执行变更都可以用自然语言发起，具体动作仍受既有权限和审批约束。

现在用 Agent 查状态、翻以前的记录，已经省了一些时间。把监控接上以后，我想先跑一遍完整的掉线调查，到需要恢复时交给人。
