飞牛 NAS 的超分与插帧应用

发表于2026-10-15|更新于2026-11-23|基础设施系统维护
|总字数:2.7k|阅读时长:9分钟|浏览量:

我原来在 NAS 上跑脚本给视频插帧，后来给飞牛做了个界面，能选片、看进度和成品目录。飞牛已经跑在 Hyper-V 里，算力用的是直接分给这台虚拟机的 Tesla P100 16 GB。

片子都在 NAS 的共享目录里，一次处理有时要好几个小时。我想从网页选完就让它去跑。跑到一半目录权限变了得停，服务重启要能找到上次做到哪，最后还得打开成品确认能播。后面的调度和检查主要是为这几件事加的。

先说实际交付。P100 真机上跑通了从选片、提交到生成并回读成品的路径。一段 1080p24 修复样片输出 48 帧、耗时 162.8 秒，保持 1920×1080、24 fps，逐帧解码通过。另有一次 4K 长片重启后能续跑，计数继续增长，但当时还没拿到最终成品。这两个样本分别验证输出和恢复，不能推导出 4K 实时处理能力。 1080p24 样片验收记录

为什么选 Hyper-V DDA

Discrete Device Assignment（DDA）把整块 PCIe 设备交给指定 Hyper-V 虚拟机。Linux 宿主用 vfio-pci 是另一条部署路线。维持现有 Hyper-V 宿主意味着不用为这张卡迁移 NAS，也不用改来宾的启动参数。宿主失去对这张卡的使用权，之后的视频处理和嵌入负载都由来宾侧安排。

验收按三步走。先确认来宾枚举到设备并绑定 NVIDIA 驱动，再从来宾查驱动与显存，最后进入推理运行环境验证 CUDA 实际可用。后两项是切换后补齐的。部署前的硬件资格、虚拟机配置和设备位置路径以 Microsoft 的 DDA 文档 为准。

App 设计：把推理容器包成飞牛应用

最初只做超分、插帧和串联处理。应用从飞牛获取登录与目录授权，Web 界面负责选片和看进度，后端拆为任务网关、推理 worker 和 GPU 准入策略。公开版后来加了去噪等处理路径。仓库列出的兼容范围是 fnOS x86 + Tesla P100，输入范围为 SDR/CFR。

超分改变画面尺寸，插帧增加时间轴上的画面数。两者都做时，先在源分辨率插帧，再把结果交给超分，避免插帧阶段先处理放大后的像素。SDR 表示标准动态范围，CFR 表示恒定帧率。这个版本的预检会把输入规格和所选模式送进同一份处理计划，界面可以在排队前把不支持的原因告诉用户。实现入口是 任务预检，各模式见 项目 README。

从用户选片开始，请求先经过任务网关。网关负责授权、预检和记录任务，运行时不直接把整片交给一个常驻请求。调度器等到有资源才开 worker，worker 解码、调用模型、输出分片，再将成品封装和回读。这个拆分的好处在重启时最明显。打开页面可以重新读任务状态，处理进度则从已经验过的分片恢复。即使 UI 刷新丢了进度条，任务和视频工作目录仍有自己的记录。

反直觉的坑：预检全绿，文件还是没写进去

早期版本预检只查”目录存不存在”，结果任务跑完写不进输出目录，白烧了二十分钟显存。反直觉的地方是：预检阶段一切正常，代价付完了才看见。

修法是把 output_writable 加进 preflight，并把最终保存路径直接显示在前端预检对话框里——用户提交前就知道文件会落在哪。可写检查的关键在身份：

飞牛应用授权和 Linux 写权限分别检查。check_output_write 先核授权根和应用 ACL，再依当前进程的有效身份检查目录写入和进入权限。部署时要让这项检查与执行任务的账号权限一致。源码和报错见 server.py。

前端提交之前读的是源文件规格、处理计划和成品目录。源文件先通过授权路径打开，再由 ffprobe 检查；成品默认放到原片旁边，回包显式带上 output_dir 和 output_writable。这样可以让用户在生成任务前修目录权限。进入队列后，调度器还要重新看 GPU 准入和资源余量。这两步分开后，一次短时显存不足也不会被误报成片源本身不受支持。

队列与验收：把”完成”的定义写进产品逻辑

应用把视频任务放进 SQLite，一次只启动一个 worker。调度器按任务创建顺序检查候选任务，在启动前用锁重新核对状态。下面是调度过程的节选：

同一张卡还会被嵌入服务使用，应用内单并发只约束视频任务。外部负载交给 GPU 准入规则处理，资源不足时可以保留任务，等下一轮重新检查。任务状态持久化在 jobs 表，视频分片能否续跑另由检查点决定。调度器和资源判断分别见 server.py 与 guard.py。

长片分片编码。每片先用解包计数核对包数，再检查尺寸和帧率，通过后写入 SHA-256。续跑时重新核对已提交的分片。整片封装完成后，再逐帧解码检查成品。这两处检查分别防止复用错误的中间产物，以及把损坏的最终文件标为完成。

加最后一层检查是因为早期插帧样片的元数据都对，重新封装后却报 H.264 码流解析错误。我把模型移出复现，只保留 FFmpeg 重封装，确认问题仍在，才去修码流格式转换。原任务改记失败。后来的样片需要逐帧解码无错才能算通过。下面是检查过程的节选：

分片哈希用来判断中间产物能否复用。最后一次解码核对的是成品的时长、帧数、尺寸与实际帧率，音轨及字幕则按任务预期检查。分片检查点和成品检查分别见 worker.py 的分片校验 与 成品回读。

错误路径不吞。 非 JSON 错误（OOM、网关 HTML 页）归一成一条固定文案：JSON 带 error 就用它，不带就兜底；日志留末 1500 字节进任务状态。

显存规划：一张卡两个主人

这张 P100 当时也给 WeKnora 嵌入池 用。嵌入需要及时响应，视频可以排队，因此视频模型按任务加载，资源冲突时先让嵌入继续跑。视频任务得承担一次重新加载的耗时，共用显卡期间也不承诺两个负载都能满速。

单并发只能防两个视频任务抢同一张卡，保护不了旁边的嵌入服务。因此调度器启动 worker 后还会定期核对目录授权和资源状态。worker 可以在分片边界主动让出 GPU，把已提交的分片保留下来。应用重启时，能识别出兼容流水线版本的活动任务会被记为等待恢复，旧任务如果没有可靠检查点则保留中断状态。这样同一份 SQLite 里的记录可以继续用，检查点仍要按它自己的规则重新核实。 重启时的任务恢复 · 运行中的授权与 GPU 检查

已跑通的部分

在当时的 P100 上，我跑通了从应用选片、检查输出路径、提交任务，到生成和回读成品的流程。4K 样片有过降档处理记录，未形成稳定 60 fps 的结论。目标输出帧率和处理速度是两个指标。要比较硬件或模型，还要在相同片源、模型、编码规格下同时记录两者。

有一轮 4K 长片在应用中心重启后被标为失败，检查点仍在。恢复任务后，计数从 33,936 增到 33,984，说明 worker 又开始处理。那份记录收尾时，整片尚未完成，成品回读和抽帧目检也未完成。我把这次结果记作恢复成功，成品验收留空。

我把界面的提示做成三种。CPU 预览用缩小的输入跑流程，GPU 样片用原尺寸处理一小段，整片跑完才显示成品的尺寸、帧率和时长。看风格、试设置，用样片省时间。音轨、封装和长片用时得等整片。想顺代码看，从预检一路读到启动 worker，再看成品检查怎样写回任务。成品检查 · 三种结果的界面提示

私人环境里曾遇到整包升级覆盖热修，后来把热修绑定到具体应用版本。本文对应公开源码的版本号是 0.3.12。项目仓库提供源码、打包和测试脚本，公开仓未附 .fpk 安装包、模型权重或运行包。飞牛跨大版本升级后的直通表现仍待复测。
