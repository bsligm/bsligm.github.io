用 WinRM 和 SSH 管理 Windows Server

发表于2026-10-01|更新于2026-11-23|系统运维系统维护
|总字数:1.3k|阅读时长:3分钟|浏览量:

从 Mac 管两台域控和一台 Hyper-V 宿主，我平时走 WinRM，SSH 留作备用。最初碰到的是命令里引号一多就很难知道出错在哪一层。后来把长脚本改走文件才看清楚。

我需要同一条执行路径兼顾新脚本和旧任务，还要保留维护窗口里能读状态的第二条路。共享目录加计划任务也考虑过，但会多三处得对账的状态：脚本有没有投递成功、任务以哪个身份运行、结果能不能取回。最后我用 WinRM 作常规入口，标准输出、标准错误和退出码三路各收各的。SSH 已经能用，就留下应付主通道临时不可用。

连接与执行引擎分开核

WinRM 是远程管理通道。客户端常用的 run_ps 会调用 Windows PowerShell；装过 PowerShell 7 也不能据此认为远端脚本自动跑在 7。三台机器都保留原来的 5.1，把 7 并行安装。依赖 7 的任务明确选 pwsh，执行前读回实际版本，旧任务继续照原来的入口跑。

如果是在安装脚本那一个终端里试 pwsh，它看到的环境可能和远程服务不一样。我习惯关掉连接重新开一个，从那边读版本。原来跑 5.1 的任务走原入口，需要 7 的任务再显式指定 pwsh。

-EncodedCommand 的输入用 UTF-16LE。远端输出我用 UTF-8 读。两边弄反以后，脚本可能已经成功退出，中文日志还是乱码。只读任务还要确认输出里有要查的对象，写任务跑完再查一次目标状态。

实测组合是 Python 3.11、pywinrm 0.5.0 与 pyspnego 0.12.4。换新 Python 时，认证依赖的安装先出了问题。锁住能跑的解释器和依赖后，可以用三条短命令做接入检查：读当前 PowerShell 版本、输出一行中文、返回一个预期的非零退出码。三项各测一层：远端引擎、客户端解码、出错传播。哪项失败就先排哪层。

长脚本改走文件

有次把多步维护拼成一条远程命令，客户端报不出足够信息，远端却卡在命令长度或解析上。后来把只读短命令保留为直接调用，较长的脚本走受控文件传输，核完整性后执行，再用同样的结果格式读回。原现场的分流阈值来自那套客户端、编码和命令包裹方式，不能当成 WinRM 的通用上限。

现场用约 1,900 个源脚本字符作分流线，给引号和编码包裹留余量。这条线只对那套脚本成立，移植到别处应在客户端对最终序列化参数做长度检查。预期有业务输出却只收到零退出码时，先核目标对象或任务状态能否读回。

两路付出的成本不同。短命令直接发，省掉每次上传；长脚本要为临时文件建立归属、核对传输结果、再做一次执行确认。长脚本如果卡在传输阶段可以就地停止。要是已经进了执行阶段，回包失败就按「结果未知」处理。这个区别比脚本到底少传了几百个字符更重要，尤其是脚本里有修改服务状态的动作。

客户端拿到的结果 编排侧处理
正常返回，且读到了目标对象 记录成功及实际引擎版本
返回非零退出码 记下退出码和经脱敏的错误，走该任务的失败分支
请求已发出，响应超时 先按任务标识查有无执行记录，写操作不直接重发
主通道在执行前连不上 独立确认备选通道，记录实际使用的路径

这也解决了降级重试的一类风险。若请求已经发出但回包超时，先检查目标状态和任务记录，再决定是否重试。只有确认主通道在执行前不可用，才切到 SSH 跑同样的操作。

以只读清点虚拟机为例，我倾向让调用端记下下面这些字段。值是检查项示意，未引用实际主机和执行结果。一个容易漏掉的情况是返回了可解析的空列表。脚本层可以成功退出，清点仍需按任务预期判断是否读到了需要的对象。

SSH 实际顶住了哪一次

补丁窗口里有一台域控已经起来，WinRM 还没启动。那轮巡检我从 SSH 做完，结果上也写了实际入口。SSH 目前只在这一次维护窗口里承担了这个备用角色。

这套方案当时只在受控管理网段运行，没上 TLS 端点和 Kerberos，跨网用之前得重新评估传输和认证。凭据按主机角色和任务权限配置。域控和虚拟化宿主分开授权，例行读状态无需获得系统管理权限。
