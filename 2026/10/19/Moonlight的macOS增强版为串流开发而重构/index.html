为串流开发重构 Moonlight：macOS 增强版的八周记录

发表于2026-10-19|更新于2026-11-23|系统维护桌面维护
|总字数:2k|阅读时长:6分钟|浏览量:

我在 Mac 上调试游戏串流。有些参数改一次就得翻一次 plist，设备偶尔掉线时，列表还会留着上一轮的结果。手工改配置能解决一次问题，第二天换设备重测又得从头核对。我保留台式机端的 Sunshine 服务，花了八周改 Moonlight macOS 客户端，先把常调的参数搬进设置页，再加上能回看的设备和会话诊断。

Sunshine 在台式机上捕获和编码画面，Mac 上的 Moonlight 接收、解码并显示，再把键盘和手柄输入送回去。改客户端设置时，得分清哪些选项会在开始串流时与主机协商，哪些只会改变 Mac 本机的显示或输入行为。比如提高客户端的目标帧率，需要主机实际按相应速率出帧，Mac 本地的设备列表则由 macOS 枚举。

先改每天都要用的地方

动手前先把”增强”落到一张可勾选的清单上，每一项有明确的验收方式：

  • 设置页收拢串流、视频、音频、输入、应用和设备六组设置。本文涉及的常调参数可以直接在界面修改。
  • 视频页集中显示编解码、分辨率、帧率和色彩选项。可用组合由客户端与串流主机共同决定。
  • USB 诊断页刷新本机设备列表，拔插后按新一轮扫描更新。USB 重定向仍处于冻结状态。
  • 会话诊断在运行中写入近期状态，下次启动可回看已写入的记录。

我把验收拆成能从记录里读出的状态与必须上机操作的场景。设备列表可以检查扫描结果，画面和输入则需要实际串流。缺第二台机器的记录，就把该机型留在待验列表里。

会话摘要按低频事件写入，出了问题可以回看已经写下的状态。异常退出可能留下一条不完整的尾记录，回读时只采用能解析的事件。诊断信息分享前需要脱敏。

同一个审计任务为何耗时差十倍

当时一项审计和构建、其他测试争用同一台 macOS runner，并发时触发了原有超时，日志最后只剩 Terminated: 15。同一审计单独运行约 140 秒，争用时曾超过半小时。这个对照把排查范围缩到了调度和资源，单看 SIGTERM 无法做同样的判断。

处理分三层：

  1. 用同一项审计做单跑对照，核对超时记录与当时并行的作业。
  2. 分支已有合并请求时，由合并请求流水线执行相同检查，减少重复排队。
  3. 审计按测得的最慢一轮单独调整预算，构建继续使用原来的超时。

以上仅节选重复流水线的排除规则。运行合并请求和默认分支流水线的规则仍需完整配置。耗时最长的变异测试单独串行，避免和日常门禁反复争抢同一资源。

出包侧：版本号只认构建产物

构建时曾遇到 CI 传入的版本和打包读取的版本不一致。出包环节从已经构建的 App 读短版本号和构建号，并在暂存副本完成资源安装后再签名。下面只展示读取版本的部分。GitHub Release 的公开附件使用架构标识命名。

实机记录

串流流畅度容易被平均帧率掩盖。我给现场记录保留了每个采样窗口的 fps 和 frameP95。后者是该窗口的帧时间第 95 百分位，用来看较慢的一端。原生路径日志有 148 条记录，窗口帧率中位数是 31.88，对应的帧时间 P95 中位数为 44.444 ms。仅缩放的一组有 139 条，分别是 62.63 和 27.777 ms。这里取的是各采样窗口数值的中位数，未把原始帧并在一起重新计算分位数。

两组帧率基线已经不同，记录可以帮助找到值得继续追的路径，无法单凭这组数字把差异归给缩放功能。要继续定位，应固定主机输出和客户端刷新率，逐次只改一个设置，再一起核对帧时间和提交等待。 原生路径记录 · 仅缩放记录

八周后，我在自己的 Mac 上日常串流时，已经能从设置页调整常用参数，断连后回看会话摘要，排查设备时也能刷新本机 USB 列表。USB 重定向的端到端测试没有完成，公开 README 将它列为冻结项。第二台不同芯片代际的 Mac 也未进行同样的验收。

串流占卡前，先把台式机从推理池摘掉

被串流的台式机平时也承担对话推理。做长时间串流测试前，我先从 WeKnora 路由 摘掉这台机器，再停本机模型服务。串流期间其他推理池继续接收请求。台式机要重新接回时，先用一次真实请求确认模型就绪，再把流量放回来。
