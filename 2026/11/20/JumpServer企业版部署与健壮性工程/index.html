JumpServer 企业版部署与 Agent 接入

发表于2026-11-20|更新于2026-11-23|系统运维安全管理
|总字数:4.2k|阅读时长:13分钟|浏览量:

用户能进 JumpServer，也看得到资产，连网站时却报 500。当时 12 个业务容器都是绿的。这个问题后来是顺着连接分配查出来的。装机、目录组同步和 Agent 的测试也记在这篇。

2023 年写过一篇《JumpServer 单节点无外置数据库部署》，讲的是一套环境怎样装起来。这次我负责的是团队访问链路的日常运行，涉及目录组同步、会话诊断、备份和恢复。最后才接上 Agent 做资产查询与试点纳管。

JumpServer 企业版 4.10 装在一台虚拟机里。员工用目录账号登录，选有权访问的资产，接入组件用对应协议连过去。后面查 500 时，我按这个顺序找，先看哪一步已经走过。

单节点能解决什么，哪类故障要另留退路

给现有部署列几类故障，分别确定由哪一层恢复。

故障 对策
容器挂了 Docker 自动恢复策略 + 组件级 jmsctl restart，不做整栈循环重启
数据库坏了 每日 pg_dump 原子备份 + 升级前强制 dump + 按时间戳命名的回退点
宿主机或盘故障 独立存储目标上的备份，并用隔离环境演练恢复
没人知道它病了 两分钟粒度健康巡检，状态原子落盘，接 Zabbix，失鲜也告警
升级升不上去 升级前必须有 dump；回退路径事先走通过一次

备份拷出来后先试着读一遍。换到一台干净机器还能不能恢复出登录、连接和录像，要另找时间演练，异地副本也得实际取回来一次。

承载与运维通道

虚拟机设计

项 值 说明
承载 PVE 单节点上的一台 VM 宿主机单节点无 HA，风险已标注
OS Ubuntu 26.04.1 LTS ostype l26
网络 单网卡入 VLAN，与业务平面隔离 堡垒机流量与业务流量分 VLAN

开机自启 启动链内 宿主机重启后自动恢复

堡垒机自己的救援入口

堡垒机断开时，管理员还要能拿到日志、读出服务状态并处置故障。给它预留一条经虚拟化管理面的救援路径。宿主侧操作继承虚拟化管理面的高权限，单独管授权与审计。Agent 的应用访问身份和日常巡检身份都不复用这条路径。

从启动容器到接入第一台测试机

这套部署可以先在一台授权测试机上复现。确认虚拟机时钟、DNS、存储容量和维护入口后，按同一发行版的安装器拉起组件。Web 能登录时，用测试用户进组织，检查它能否看到指定资产并用约定账号打开会话。连接结束后到审计台找记录。这个样本能跑通，再加第二种协议和目录同步，出错时比较容易判断是公共入口故障还是单条连接链的问题。

网络的回验按方向做。客户端到 Web 和协议入口、协议入口到目标、应用到目录服务。测试源也要选对，从堡垒机宿主访问到预期目标，与真实用户从办公网连接是两条证据。生产入口要按组织要求验证 TLS、证书链和管理可达性，文中的安装记录不能替代这些验收。

版本选型：一次失败升级教会的事

时间线：

  1. 初装社区版 4.10.19
  2. 试用企业版，生产稳定在 v4.10.18-ee
  3. 2026-09 一次 v5.0.0 升级尝试，两周内判定失败，回退 ee

当时借助升级前的数据库归档做了回退。单次回退能恢复原版本，完整环境仍需独立恢复演练。后来把可重复核对的部分拆成了三项：

  • 升级前留存可识别的备份和版本记录。 先查归档生成结果，再验证目录可读。同时记录数据库、应用配置、密钥恢复材料与会话存储范围，单个数据库包不足以覆盖整套环境。
  • 回退路径必须事先走通一次。我们这次是「恰好」回退成功，不算验证；验证标准是回退演练过
  • 升级残留要当故障源管理：v5 的 kael 容器停在 Exited、1.4 GB 的安装包和解压目录留在 /opt/——只要残留还在，下次误操作就可能二次翻车。残留不删，升级就没结束

网络取舍两个：

  • 业务接入与数据库管理分开。 业务侧通过 JumpServer 提供的访问入口连接资产。维护数据库走受控管理路径。验收时分别核对容器内监听、宿主端口发布与业务网可达性。
  • 容器网段 DOCKER_SUBNET 独立成段，与业务网段、宿主网段都不重叠。跳板机的容器内部网络是最容易被当成「反正不对外」的地方，出问题时反而最难查——独立网段让 ip route 一眼分清内外。

备份、巡检、目录同步与日志轮转

日常备份、巡检、部门同步和日志轮转各有独立计划与回退对象。巡检另外核对本轮采样时间，避免读到上一次留下的绿灯。

1. 每日数据库备份（jms-daily-backup.timer，每日 03:10，漏跑补跑）

归档先写入备份目标目录中的临时文件。确认 pg_dump 成功，并用 pg_restore --list 读出归档目录，再在同目录改名发布。磁盘写满或数据库连接中断时，让作业报错，保留上一次有效备份。

备份目标目录限制为备份账户访问。归档目录可读只完成第一道检查，数据、所需密钥和应用状态仍要在隔离环境里做恢复演练。失败暂存按备份作业的保留策略处理，不参与有效备份轮转。PostgreSQL 的归档目录说明

2. 两分钟健康巡检（jms-health.timer）

巡检不是 docker ps 看一眼就完事，检查项分四层：

层 检查项
容器 12 个业务容器健康状态
数据 PostgreSQL 可查询、Redis 响应
入口 Web 健康接口、RDP 发布机 3389、启用中的远程应用是否有成功发布与在线发布机
自身 每日备份的时效（昨天有没有跑成）、日志属主、轮转失败状态

两个关键机制：

  • 状态原子落盘：结果写 /var/lib/jms-health/current.json，原子替换。下游（Zabbix、值班脚本）读到的永远是完整文件，不会出现读到一半的状态
  • 失鲜独立告警：健康值的采样时间戳单独一个 Zabbix 对象，文件停止更新本身就是告警——巡检挂了比业务挂了更可怕，因为它让你以为业务还活着

Zabbix 侧四个对象：原始状态、健康值、采样时间戳，再加异常与失鲜两条告警规则。失鲜规则盯时间戳不盯数值，专治「旧文件假绿」。

3. LDAP 登录和部门映射分两层

JumpServer 通过 LDAP 对接目录，登录范围由 Base DN 与过滤条件限定。先用测试账户核对启用、禁用和迁移部门三种情况。Base DN 过窄会漏人，过宽则可能带进服务账号和无关组织。

部门权限单独同步。脚本读取目录状态，按映射表计算受管用户组的期望成员，再与 JumpServer 现状比对，只写差异。只允许改清单中的业务组，系统组保留原状。移出部门和离职需要走不同的管理流程，不能把定时同步的时间窗口当成即时撤权。

举个脱敏例子。一个人从开发组转到质量组，登录身份可能保持不变，变化的是两个受管组的成员关系。同步要同时算出旧组移除、新组新增，写完回读两组。能否看到目标资产还要看质量组对应的资产授权。反过来，目录查询超时应记为没有拿到输入，不能把空结果当作组织里没人。

我用相同的目录快照重复执行过同步，结果保持一致。每轮先看增删清单，再回读实际组成员；如果目录查询失败，保留当前授权，避免把查询故障误当成全量删人。

4. 日志轮转收口

加固前日志轮转规则重复且属主混乱，rsyslog 新旧规则打架。收口方式：保留发行版 rsyslog 规则的 12 份轮转与 50 MiB 阈值，旧重复规则改成说明文件归档，新规则指定 syslog:adm / 0640，修正现存日志属主，logrotate -d 调试加实跑双验证，全程不重启日志服务。合并前先确认没有业务在依赖旧规则的轮转间隔——这条比改配置本身容易踩坑。

登录正常却连不上，怎样定位那次 500

登录和资产列表都能用，只有部分网站资产的连接选项返回 500。巡检当时看到 12 个业务容器健康，也没有内存耗尽的迹象。这个组合能排除明显的整栈停机，定位应从该协议经过的组件往下走。

沿着连接分配查下去，找到一条还启用着的旧应用记录，底下已经没有可用的发布实例。我只停用了它。连接选项回来以后，又从浏览器进去、正常退出，再去审计里找这次的会话 ID，找到了约 1.8 MB 的归档录像。做到这里，才知道用户的操作和录像都回来了。

巡检因此还要看已启用的连接方式是否具备有效发布目标。容器探针继续保留，历史离线记录和现有用户连接失败分别统计，否则升级后的遗留记录会遮住真实故障。

Agent 能读什么、能改什么，怎么验收

让 Codex 帮我管一台服务器，我通常先问清楚要做哪件事。查谁有权登录、给研发组加一台资产，走 JumpServer API。要装软件、改系统配置，或者升级 JumpServer 本身，就得登录对应的机器。两条路可以用在同一件事上，拿到的权限各归各。

JumpServer API 能做到哪

对接时，Codex 调用的是执行工具，由工具用服务账号的 Access Key 签名。密钥放在受控的凭据入口，返回给 Codex 的只有所需字段和操作结果。比如我问「质量组现在能连哪些机器」，它先查指定组织里的组和成员，再把直接授权、组授权和节点授权对起来，就能列出哪些资产、用哪个登录账号、走什么协议、权限到什么时候。给了审计权限，还能按时间和资产查在线或历史会话，看到是谁连的、用的哪个账号。API 认证 · 角色列表 · 会话记录

有写权限时，可以新增或更新资产、登记资产登录账号、维护用户组成员，也能创建、修改或撤回资产授权，具体看这套实例提供的接口和执行账号在组织里的角色。我会让它先查已有记录，拿到资产和用户组的 ID，再列出准备改哪些字段。获准后才写，写完按同一个 ID 查一次。接口超时先查这笔变更到底有没有生效，免得再加一条。LDAP 同步来的组，要回到前面那套目录同步规则看成员从哪来。资产授权的字段与范围

给了 OS 账号之后

给到目标机的 OS 用户名和密码，我可以让 Codex 从获准的连接入口登录。登录前核对目标，密码由执行工具使用，聊天和日志里只留检查结果。普通账号能查它有权读取的系统版本、服务状态、日志和文件。明确授予维护权限以后，才有相应的权限装软件、打补丁、改配置、启停服务或做备份。这些权限由机器本身决定，JumpServer 上能连这台资产只是登录这一步。

拿升级 JumpServer 举例，登录的是运行 JumpServer 的那台 Linux 主机，用的是单独授权的维护账号。Codex 可以先盘点版本、组件和存储，核对目标版本、备份和回退条件，再在批准的窗口走发行版支持的升级方式。升级完，先读运行版本和服务状态，再拿测试用户登录、连一台代表性的资产，最后查那次会话及应有的录像。中途失败，就保留当前状态，按约定的条件处理回退。经堡垒机走的连接按实际协议和录制设置查审计，从救援入口直连的维护按该入口留操作记录。单机升级指南 · 备份和恢复

把一台新机器交给研发时，两条路都用得上。先让 Codex 用 OS 账号确认主机、检查要交付的服务，再用 JumpServer API 登记资产、选登录账号、给指定组加授权。最后换成那个组的测试用户，从 JumpServer 实际连一次，确认查到的就是这台机器。收回权限时，我会再查一次规则，用同一个测试用户重连。原来已打开的会话也单独确认。

这次用签名 API 跑过测试对象的创建、授权、读回和清理。前面那次 500 则实际连了网站，也查到了录像。换成收紧权限后的服务账号，再从审批、执行一直跑到撤权和失败恢复，这轮演练还没做。

给接手的人留下哪些证据

回退优先按对象恢复。变更前留存目标对象的标识和原值，出问题只撤回本次改动。整库回退会覆盖备份点以后其他人的正常变更，需要独立审批并先评估影响。

已经验证的是数据库备份可读、巡检状态可以采集、部门映射可重复执行，以及网站连接恢复后可以读回录像。完整恢复、告警实际送达、授权自动回收和 Agent 收权后的全流程仍需单独演练。备份可读只覆盖备份格式，不能替代恢复到干净环境并验证登录、连接、录像与密钥可用。

把故障交给下一班时，我会给出变更号、授权对象和实际会话 ID。这样他能自己点开那段连接或录像，知道用户是不是用上了。需要撤回时，再从记录里找旧配置和当时还没验证完的项。
