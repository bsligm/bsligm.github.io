三台域控部署实录：两台本地加一台云上的 AD 落地与十个坑

发表于2026-11-19|更新于2026-11-20|系统运维基础设施
|总字数:4.3k|阅读时长:13分钟|浏览量:

本地机房一台 PVE 跑两台域控，云上一台 ECS 做第三台，外加证书服务器和远程桌面网关。三个多月下来，主线之外的坑比主线还长。这篇按部署顺序记三台域控的落地过程，公司相关的地址、主机名、域名、凭据一律不带；只有历史记录、没有复测的结论单独标出来。

拓扑与角色分工

角色 位置 系统 说明
DC1 本地 PVE 虚拟机 Windows Server 2025 主域控，兼 DNS
DC2 本地 PVE 虚拟机 Windows Server 2025 第二域控，与 DC1 同站点
DC3 云上 ECS Windows Server 2025 Datacenter 云上域控，独立网段，与本地经隧道互联
证书服务器 本地 PVE 虚拟机 Windows Server AD CS 企业 CA，签机器证书与 LDAPS
远程桌面网关 本地 PVE 虚拟机 Windows Server 2025 RD Gateway，公网 443 收 RDP

三台域控是审计确认后的形态。DC1/DC2 从一开始就是域控；DC3 八月初交付时按当时的要求只做了系统初始化、没装 AD 角色，几天内才提升为域控。提升前那轮准备工作（改名、静态地址、DNS 指向本地 DC、安全基线对齐）是后面几乎零返工的原因，下面单独讲。

单台机器从裸机到提升为域控的分步手顺，早年写过一篇 Windows Server 安装以及 AD 域服务搭建，域名、功能级别、DSRM 密码这些不可回退的取值都在那篇里。本文不重复，只讲三台规模之后才出现的问题。

例行审计记录的 FSMO 角色里，PDC Emulator、RID Master、Infrastructure Master 三项都在 DC1；另外两项角色当时的审计表没有列出，不在此文断言。

虚拟化层：PVE 上跑 Windows 域控的对齐清单

域控对虚拟化的要求不多，但每一条都影响能不能装、装完稳不稳。逐项核对过的配置：

  • 固件必须 OVMF + Secure Boot + TPM 2.0。Server 2025 的若干安全特性默认要求这些，PVE 侧对应 OVMF 固件加 vTPM 状态盘，EFI 用 4M 类型并预注册微软密钥。这三项配齐的虚拟机，后来才具备跑 BitLocker 计划的前提。
  • 磁盘接口。初建的域控用 IDE 挂系统盘，PVE 新建 Windows 虚机的默认懒路，代价是 I/O 性能比 virtio-scsi 加 iothread 低三成以上。换接口要同时改启动顺序，并提前注入 virtio 驱动，否则起来找不到盘。
  • Hyper-V enlightenments 全开。hv_relaxed、hv_synic、hv_stimer 这一组给 Windows 客户机减负，PVE 对 Windows 机型模板只默认开一部分，逐项补全后 CPU 等待明显收敛。
  • 禁用睡眠和休眠（disable_s3=1、disable_s4=1）。域控睡过去一次，Kerberos 时间偏差和复制积压就够排查半天。
  • CPU 型号至少 x86-64-v2-AES，能直通用 host；8 核以上启用 NUMA 绑定。ostype 别随手写客户端机型，机型模板会连带决定默认设备组合。
  • 时钟：RTC 用 driftfix=slew，全集群统一 base 取 localtime 还是 UTC，混用会出现开机时间跳变。

PVE 宿主本身审计出的问题也值得列，基本都是”默认装机就不会有”的项：主机防火墙未启用、ZFS 数据池未加密、vzdump 备份只有符号链接没有实际配置和保留策略、无 HA 单点、root 无 MFA。当时综合评分给了 63%。这份清单留作整改基线，截至发稿宿主防火墙和实际备份仍未整改，属于已知未闭环。

安全基线：从 77 分到 89 分动了哪些项

DC1 上线初期做过一次全盘安全审计，修复后重启复验，评分 77% 提到 89%。真正值得记的是修复过程中的几个具体坑。

NetBIOS 的 139 端口关不干净。 逐网卡把注册表 NetBT\Parameters\Interfaces\...\NetbiosOptions 设为 2 并重启，端口仍在监听——承载者是内核（PID 4），sc stop 无从下手。最终接受的做法是注册表禁用加防火墙在 Public profile 上对 137/138/139 加阻止规则兜底：监听仍在内网地址上，只是外部不可达。这个行为微软社区讨论多年，结论基本就是防火墙兜底为正解。

WinRM 的 HTTP 监听绑在 IPv6 全接口。 用 netsh http show servicestate 才看到通配监听，而 WinRM 的 IPv4 防火墙规则对 v6 监听完全不生效。给 5985 补限段规则（只允许管理与办公网段）后收口；RDP 3389 同理补限段，公网面由上游防火墙负责。

LDAP 通道签名。 注册表 LdapSigning=1，重启域控后生效。没有域内测试环境，这类注册表手术前按惯例给相关虚机打了快照再动手（审计前的快照清单里就有这几台），改完确认 Netlogon、KDC、ADWS 全部正常再保留。快照不是备份，但能让一次改动有后悔药。

SMB 基线三件套：卸载 SMB1、启用签名、启用加密。注意 Server 2025 上签名参数的名称与旧版本不同，脚本照抄旧文章会静默失败。

后来 DC3 提升前、远程桌面网关上线前，都拿同一张对齐表逐台核过。每台多花二十分钟，换来三台行为一致。跨版本环境里”每台默认值不一样”才是最大隐患，基线表是性价比最高的防御。

证书：一张指错目标的机器证书

八月中旬审计发现 DC2 的机器证书指向了错误目标主机，走 LDAPS 的客户端校验会失败。修复本身不复杂：重建请求、按正确 SAN 签发、重启依赖服务。留下的尾巴是当时的临时方案——一套自签续期脚本以 SYSTEM 计划任务部署到三台域控，命令行不含明文凭据（脚本上机前跑过凭据关键词扫描）；域内企业 CA 就绪后，域控证书改由内部 CA 签发，这套自签脚本就成了历史遗留。历史记录显示计划任务仍在，是否与 CA 方案冲突没有复测，这条只能记成”历史说法”。

通用教训：机器证书的 SAN 必须在请求阶段核对。 签发后才发现指错，回滚成本远大于前置检查。现在的做法是签发脚本里硬校验 SAN 与主机 FQDN 一致才提交。

时间源：域控的 NTP 别用默认

PDC Emulator 是全林时间源，默认取时地址在国内办公网的表现是同步间隔拉长、偏差爬到分钟级、Kerberos 开始报 clock skew。

实测结论：多个公共 NTP 从业务网不可达或抖动严重，逐个探测后固定一家延迟稳定的国内源并配备用源；非 PDC 域控全部回归默认层级跟随 PDC，不做”每台都指公网”这种画蛇添足。改完用 w32tm /resync /force 验证，偏差回落到毫秒级。

坑在于 w32tm 的生效链很长：组策略、注册表、手动配置三层，手动配置会被组策略周期刷回。改完当场正常、几周后复发，基本都是策略里还压着旧值。查时间问题先跑 w32tm /query /source 和 /query /configuration，确认当前真实生效层，别一上来就调 syncfrom。

最大的坑：内网域名和官网域名同名

三个月里最花时间的问题。AD 域名和官网主域名用了同一个字符串——这不是错误配置，当年建域时内外同名是常见做法，官网也在同一个品牌域下。麻烦在于：办公网的 DNS 查询全部走内网域控，裸域名解析回来的是三台域控的内网地址，浏览器打官网就撞在域控的 80/443 上——域控上没有 Web 服务，连接被拒。带 www 的记录指向公网，所以 www 正常、只有裸域炸。内部区里还残留历史时期手工加的 www 公网记录，与公网权威解析已经不一致，属于同一根因的次生问题。

候选方案按侵入性排序：内网 DNS 做条件转发、客户端侧代理、或者域控直接转发。前两者分别动全局 DNS 和所有终端，被否。最终落地对域控侵入最小的一种：三台域控各加两条 Windows 原生 portproxy，把本机私网地址的 TCP 80/443 转发到官网 www 的公网端点，防火墙只放行办公网段到域控 80/443 且限定进程 svchost。请求经域控跳板后 301 到 www，后续流量直达公网，域控不终止 TLS、不经手证书链。

实施里踩的坑比方案本身更有教育意义：

  1. 转发目标不能用裸域名的解析结果。上游名称如果解析回域控自己，直接形成回环。部署前检查里必须确认上游解析出的是公网地址。
  2. 首轮试点失败过，失败点是持久性。首轮防火墙规则按进程匹配放行，并用一条计划任务做健康探测、异常自动回退。上线后发现规则没能留存，而探测任务跑在管理员远程会话的子进程树里，会话断开时守卫跟着一起没了。重做版改为 SYSTEM 账户的独立计划任务，规则改成按本机私网地址加端口加进程精确匹配，并把旧 IIS 默认站点的自动启动关掉（只改 serverAutoStart 一个属性，保留 Web 服务运行），防止未来某天 IIS 把 80 抢回去。这套”守卫 + 超时自动回退”后来真的被触发过一次并成功回退。
  3. 回退必须按任务边界设计。每台域控留一个独立发布目录：变更前配置快照、原始 IIS 配置、回滚脚本及其哈希。回滚只撤销本任务新增的两条转发和精确防火墙规则、恢复站点自动启动值，绝不 reset 全部 portproxy、不整份还原防火墙或 DNS——域控上别人家的规则与你无关。云上那台的等效动作是安全组只删本任务新增的规则 ID，原有二十余条逐项保留。
  4. 验收要覆盖域功能，不只是网页。改的是域控的网络栈，网页跳转只占验收清单小半：三台复制失败计数、LDAPS 握手、SYSVOL 与 NETLOGON 可读、GPO 目录、LDAP SRV 记录、关键服务 PID 与变更前基线一致。两百多项入口检查和十余次客户端完整链路之外，这些才是敢在生产域控上动手的底气。

未闭环也记在这：内部区里那条历史 www 记录没清理（实测当前可用，动它需要单独评审）；没做生产重启演练，所以”重启后依然生效”只能说配置层面成立、没有实测；官网源站的偶发连接失败只做了有界复测。

云上域控：一台 1 核 8G 的 ECS 敢不敢当 DC

DC3 的配置单拿出来看是劝退的：1 vCPU、8GB 内存。但小规格域控在中小企业混合云里非常常见，能跑的前提是角色预期要诚实——价值是本地整体断线时认证不至于全灭，以及给云上业务提供就近认证，不是拿来扛负载的。

要点：

  • 初始化阶段就完成与本地域控完全一致的安全基线（SMB 三件套、LDAP 签名、NetBIOS 禁用、RDP NLA、防火墙三 profile 启用），提升为域控后不用再补作业。
  • 安全组只对管理网段放行远程管理和 WinRM，不对公网开放任何 AD 端口；复制与认证流量走与本地的隧道。
  • DNS 首选/备用指向本地两台域控，云上私有网络自定义 DNS 参与域解析，否则域成员找不到 SRV 记录。
  • 时间源在云上更隐蔽：云主机默认走云厂商内部时钟源，提升成域控后要按域内层级逻辑重新审视它的时间来源，别让”云默认”和”域默认”打架。

八月的例行审计里，三台域控复制 0 失败、延迟在站点链接允许的窗口内，这台小机器没有任何性能相关告警。

pwdLastSet=0：一次”嫌疑犯不是凶手”的排查

十一月排查下游身份同步平台批量写密码失败，第一嫌疑人是”下次登录必须改密”标记（pwdLastSet=0）。全林扫描结果：一百多个用户对象里只有 9 个带标记，且全部是禁用账号（8 个普通账号加内置 Guest），与失败的那批启用账号完全不重叠。

处理与三点收获：

  1. 清理在 PDC Emulator 上执行，Set-ADUser -ChangePasswordAtLogon:$false（等效写入 -1），8/8 成功，逐对象回读确认 userAccountControl 没被顺手改动，内置 Guest 原样不碰——不在范围内就不动。
  2. 跨站点复制延迟差点骗过验收。本地域控已收到变更，云上域控短时间内还没收到复制更新，在它上面复核会得出”没改成”的假象。确认属于复制节奏正常后，用 Sync-ADObject 对这批对象做单对象同步（不动复制拓扑和站点计划），三台视图一致才算完成。多域控环境”写一台、验三台”必须是默认动作，且验证要接受复制延迟窗口，拿单次快照下结论必然误判。
  3. 结论必须诚实：清标记不等于修故障。批量写密码失败的根因不在这次清理里。首次写入的正确顺序（LDAPS 写密成功、再清强制改密标记、回读 pwdLastSet>0、用专用测试账号验证首同步与改密）已写进对接方案，但真实首同步链路没验收，此项到发稿仍未闭环。顺带否掉两种野路子：用”密码永不过期”绕标记是在改密码策略；写脚本周期性全域清标记会覆盖管理员主动设置的强制改密。两者都比原问题更糟。

零碎但值得记的

  • RD Gateway 可以纯注册表配置。纯远程 PowerShell 场景下官方 cmdlet 依赖的部署上下文不完整，认证模式、设备策略、审计开关直接写 Terminal Server 的 Parameters 键完成，证书绑定写 GUID 子键，重启网关服务生效。图形界面和 cmdlet 不是唯一的门，但要留下注册表前后对比作为变更证据。
  • BitLocker 恢复密码入 AD。试点验证了 AD 侧备份与按 OU 授权非域管读取，但一次真实恢复演练没做完——“已实现”只能写到试点为止。没演练过的读取路径等于不存在。
  • DNS 区安全更新。四个区全部 Secure Dynamic Update，非域内主机无法往区里注册记录。这是默认值，但值得确认没人图省事开过不安全更新。
  • 运维脚本本身也要过安全审查。续期脚本上机前跑过凭据关键词扫描，计划任务运行账户回读为 SYSTEM，凭据不落命令行。自动化脚本是新的攻击面，这个习惯值得固化。
  • 远程执行链路的收尾。整个项目大量改动通过远程 PowerShell 完成，收尾时要清掉本次上传的脚本、临时 stdout、测试用的临时授权条目，并回读两端确认无残留进程与监听。长期配置和 known_hosts 不清空，也不为了重试降级主机密钥校验。

未闭环清单

发稿时点仍未关闭的项：

事项 状态
PVE 宿主防火墙、实际备份任务、宿主 MFA 未整改（审计已知）
ZFS 数据池加密 未做，依赖上一项先有备份
证书自签续期任务与内部 CA 共存 历史说法，未复测
内部 DNS 历史 www 记录 未清理，实测可用
BitLocker 真实恢复演练 未验收
下游身份同步首同步链路 方案已定，未验收

小结

三台域控本身没什么技术含量：装、提升、对齐基线，微软文档里全有。真正花时间的全是文档不会写的部分——内外同名域这种历史决策的账、复制延迟造成的验收假象、注册表与组策略的生效链打架、以及”改域控网络栈”这种动一下就要拿全域功能验收兜底的敬畏心。

只留一条经验：在生产域控上动手之前，先把回退边界和验收清单写清楚，再碰键盘。

公司环境的地址、主机名、证书指纹、安全组 ID 与凭据已全部脱敏；性能与评分数字取自当时现场报告的原始记录，未经二次复测，仅作口径参考。
