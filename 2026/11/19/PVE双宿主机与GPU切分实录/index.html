PVE 落地与 GPU 切分实录：具身智能 S2 边缘推理、L40S vGPU 与 PRO 6000 MIG

虚拟化底座是两台 PVE：一台浪潮 M7，单张 L40S，跑身份服务和桌面；一台超聚变 Pro6000，八张 RTX PRO 6000 96G，跑具身智能 S2 的边缘推理和大模型。这篇按 PVE 初始化部署、S2 负载、L40S 普通 vGPU、PRO 6000 MIG 切分、模型优化的顺序写，重点放在最后一节——三轮延迟调优，每一轮改了什么、为什么、降到多少。

地址、主机名、序列号、凭据、内部产品名都脱敏了。所有毫秒数是离线模型层的实测值，不含相机采集到机器人执行的链路。

PVE 初始化部署

项目 浪潮 M7 超聚变 Pro6000
CPU Xeon Gold 6548Y+（128 逻辑核） 2× Xeon Gold 6530，共 64C/128T
内存 503 GiB 可用 4×128 GB DDR5-5600，OS 可见约 503 GiB
GPU 1× L40S 48G 8× RTX PRO 6000 Blackwell Server Edition，各 96 GiB
数据盘 RAID 卡呈现的 7T 逻辑卷 2× 3.84T 裸 NVMe
PVE 9.2.18，内核 6.14.11-9-pve 装机 9.2.2 升到 9.2.21，内核对齐 6.14.11-9-pve

Pro6000 的 NUMA：node0 = 0-31,64-95，node1 = 32-63,96-127，后面绑核全靠这张表。

新机交付后的固定动作：

  • 企业源无订阅必然 401，先切 no-subscription；
  • GRUB 加 intel_iommu=on iommu=pt，直通和 vGPU 都靠它；
  • 黑名单 nouveau。坑在 Blackwell：nouveau 绑定直接报 unknown chipset，这代卡开源驱动完全不认，不黑名单的话闭源驱动装了也不生效；
  • chrony 加时区；运维公钥注入后关密码登录；
  • 网卡 pinning 钉成 nic0…nic7，不留 enp34s0f0 这种物理名，换卡或换内核后配置不用人肉对照。

网络：管理与业务各自一组 LACP，各自上网桥；业务桥 VLAN-aware 且故意不给 IPv4，虚拟机挂业务桥打 tag（tag=130）。桥上没有 IPv4 会被误判成”业务网不通”，它本来就不该有，当 bug 去修反而搞乱 trunk。实测踩过的坑：

  • bond 起来后成员口的当前 MAC 被 bond 统一覆盖，认领”哪个口是哪根线”只能靠 permanent MAC 加 PCIe 总线号；重装系统后 bond MAC 会变，交换机侧配了端口安全直接失联。
  • 交换机侧 lacp-static 动态聚合时，单口不协商就不转发，安装器阶段还没有 bond，直连装机器可能整个拿不到 IP，动手前先查交换机配置。
  • bond-lacp-rate 不在 PVE 的 API schema 里，GUI 不显示，只能手写 /etc/network/interfaces。真发生过一行脏内容把 bond-lacp-rate 吞掉、ifreload 还不报错的事故，靠 cat -A 加 ifreload -n -a 空跑才发现，修完在 sysfs 读回 fast 1 才算过。
  • 哈希策略不能照抄：layer2 只按源目的 MAC 哈希，网关 MAC 唯一，第二条 10G 链路发送方向近乎闲置（0.4MB 对 5.6MB），改 layer3+4 后两口都发包。但 802.3ad 下一条 TCP 流永远只走一个口，验证聚合要打多条不同五元组的流。

存储：最重要的一课是 ZFS refreservation。PVE 建 ZFS 卷默认带 refreservation，声明 500G 的盘占住 508G 额度、实际只写 4.66G，全池逻辑声明对物理写入放大 6.3 倍，表现就是”还剩 6TB，pvesm status 只给 788G，新虚拟机建不了”。处置：新盘默认 sparse=1，60 个卷里 56 个非零预留清零，可分配从 943 GiB 回到 5.59 TiB；验收记录里写清楚这是解除容量承诺，不是清出 4.67T 真实数据。精简置备的验收判据：64 GiB 卷空卷实际 57344 字节，卷首卷尾各写 4 MiB 后实际 8.125 MiB。两台机器的池结构完全不同：M7 的池是 RAID 卡呈现的单 vdev（实际 RAID-1(1+0)），ZFS 看不见底层冗余，判据靠 sysfs 的 raid_level 读回；Pro6000 两块裸 NVMe 不做 RAID，OpenZFS 原生 split 成两个单盘池，故障域独立，代价是坏一块盘那一半没副本。

启动编排：按 order 分七组（GPU 授权服务最先起最后关，推理机最后起最先关）。up 是固定 sleep 不是健康检查，同组多台都设 up 会按台数放大；没设 order 等于最后启动、最先被强杀。这套时刻表目前纯推算，未实机验证。

cloud-init：模板路线，三条纪律。PVE 配置、种子盘、来宾内状态是三个对象，页面上改了 ipconfig0 不证明来宾应用了；cloud-init clean 是模板动作不是生产动作，生产机上跑一次等于赌运气；克隆完逐项验身份，两个克隆的 machine-id 和主机密钥必须不同，漏了就是两台机器向监控报同一个身份。

具身智能 S2 边缘推理

先说负载，不然后面的数字没有参照物。S2 是一个具身智能的视觉-语言-动作模型（VLA）：BF16，三路相机输入（腕部 480×640、两路立体 540×960），148 维动作、50 步动作时域、4 步去噪、49 步实时 lookahead，推理每 32 步一次、对应 640 ms 节拍，执行窗口 8 步。也就是说每台边缘机要在 640 ms 的节拍里交出动作，模型层实测必须给相机采集、RPC、动作平滑和机器人派发留出余量。

Pro6000 上八张卡的分配：

GPU 归属 切分
0–3 601–604（S2 边缘推理） 各一张 DC-96Q 独享
4–6 667（大模型推理） 各一张 DC-96Q
7 605–608（S2 边缘推理） 四个分区，先普通 24Q 后 MIG

601 是原实例，602–604 是完整克隆（不是链接克隆，origin 为空），8 vCPU、32 GiB。内存从 16 GiB 扩到 32 GiB 的起因不是容量不够，是 VFIO 锁页撞上节点本地内存不足，触发大页整理后连带把同池另一台带挂过一次。

605–608 的来历要讲清楚，否则”24Q”和”MIG”会混：605 从 601 完整克隆；606–608 先建成无 GPU 的测试克隆（500 GiB 精简根盘，来宾内空闲块回收后实际约 56 GiB 一台）；GPU7 先切成四个普通 24Q 给四台共用，验不过，再换成四个 MIG 硬分区。四台最终 16 vCPU、32 GiB、balloon 关闭。“无 GPU 克隆”和”普通 24Q”都只是中间状态，不是交付规格。

来宾环境统一：PyTorch 2.7.1 + CUDA 12.8，OMP 4 线程、OpenBLAS 2，worker 固定 CPU 0–5。宿主驱动 580.65.05、来宾 580.65.06 配对，全部 Licensed。

L40S：普通 vGPU

L40S 机走 mdev 分片，虚拟机配置形如 hostpci0: <PCI>,mdev=nvidia-<NNNN>。要点：

  • nvidia-NNNN 的编号以本机枚举为准，不跨卡抄。同一张 L40S 上 12Q、24Q、48Q 是三个不同显存档位的 profile，八卡机上的编号又是另一套，任何文档或聊天记录里的常量都不算数；
  • mixed-size（同卡混布不同档位）要在 pve-guests.service 自动拉起虚拟机之前打开，否则重启后切分状态不对；
  • 驱动 R580 配对锁版本，DKMS 随内核构建。

一个容易搞错的边界：**L40S 是 Ada、计算能力 8.9，不在官方 MIG 支持列表里。**MIG 支持按 SKU 给，不是”计算能力够就有”。所以这张卡只有 vGPU 时间片，够身份服务和桌面用，延迟要求不苛刻；真正要抠延迟的是八卡机。

踩过的坑：pve-nvidia-sriov 服务 failed 之后重启 VF 不自建，进了巡检；授权失效在监控里反复出现，不靠降噪掩盖；显存占满 96.7% 时新增 vGPU 直接失败——单卡没有余量，容量要提前规划。

PRO 6000：MIG 切分

八张 RTX PRO 6000 Blackwell Server Edition，每卡 48 个 VF，走 SR-IOV 加 vGPU Manager。主机侧组件：pve-nvidia-vgpu-helper 加 pve-nvidia-sriov@<PCI>.service 负责开 VF；nvidia-vgpu-mgr 必须常驻，nvidia-vgpud 是 oneshot，待机时 dead 是正常的。mixed-size 用自研 unit 保证：Requires/After 八个 SR-IOV 实例与 vGPU Manager、Before=pve-guests.service，执行前校验八卡空闲且 VF 就绪，可重复运行。不做这一步，重启后只有第一张卡按预期切分。

**最凶的一条风险是内核与 DKMS。**宿主 nvidia DKMS 只为 6.14.11-9-pve 构建过，更新的内核装好了但没有对应模块编译记录，唯一防线是 GRUB_DEFAULT 硬锁。任何 update-grub 或改默认内核之前必须先核 DKMS，否则一次重启，所有依赖 vGPU 的虚拟机全废。这条在巡检清单里单列。

切分口径先说清，口头说错的概率太高：

profile 显存 说明
DC-96Q 96 GiB 整卡 1 实例
DC-48Q 48 GiB ≤2 实例
DC-32Q 32 GiB ≤3 实例
DC-24Q 24 GiB ≤4 实例，时间片共享
DC-1-24Q 24 GiB MIG 派生，1g.24gb+gfx，46 SM

**普通 DC-24Q 不是 MIG。**它固定的是显存档位，计算单元靠时间片调度共享；名字带 DC-1-* 的才是 MIG 派生（GPU Instance profile ID 47，驱动枚举 46 SM、可用 23.12 GiB）。”用 MIG 切了一卡四”这种说法听过太多次，两者的运维动作和故障面完全不同。

观念上两条：密度不等于性能——驱动能列出四个实例不代表四路延迟保得住，没有受控并发数据之前不许把单实例吞吐乘四；五个 24Q 塞不进一张 96 GiB 的卡，四个是上限。

还有一套容易混淆的数字：同一块 MIG 分区，驱动枚举可用 23.12 GiB，CUDA 看到约 23.69 GiB，来宾 nvidia-smi 报 24576 MiB——三个数都真，各答各的问题，别拿其中一个去”纠错”另一个。

MIG 的运维成本也要记：来宾内 GPU 和显存利用率字段读不出来，读到 0 是”不可读”，不是”0% 利用率”，监控侧按设备能力把这几类指标显式排除而不是灌 0；回退是复合动作——清掉本轮建的 GPU/Compute 实例、关 MIG、恢复 Best Effort 调度和监控期望，缺一环就拒绝不完整回退；宿主重启后靠 hookscript 恢复切分，钩子的冷启动持久性在未闭环清单里。

模型优化：CUDA Graph

模型层真正起作用的一件事是 CUDA Graph。S2 推理路径用 Graph wrapper 包起来，44 个图，消掉每次 kernel launch 的 CPU 侧开销，首次加载预热约 30 秒。

对照是同一套 MIG 布局上的抓球模型（四路相机输入、没有 CUDA Graph）：mean 206.5–210.4 ms、max 287.6–307.8 ms；S2 带 Graph 在同样四路并发下是 114.7–126.9 ms。两个模型输入和结构不同，不能严格解读成”Graph 省了 90 ms”，但足以支撑一个判断：对这种高频固定形状的推理，不开 CUDA Graph 基本等于浪费一半预算。

显存不是瓶颈：抓球模型峰值显存 5.28 GiB（预留 5.40），worker 最大常驻集 16.28 GiB，24 GiB 分区余量很大。瓶颈在时间。那台 96Q 生产机历史上的 104.86 ms 是动态业务日志、没有同条件权重哈希，只能当参考，不能拿来签”非劣”。

每一轮调优降延迟的思路

三轮走同一条路：先找到时间花在哪，再形成假设，尽量只改一件事，同一模型、同一批输入、同一参数复测，拆不开的变量如实写出来。

第一轮：NUMA 本地性，有效

时间去向：601 的 GPU（GPU0）在 node0，但它 16 GiB 主内存有 99.99% 落在 node1。跨节点访存跑推理，每次 kernel 都要穿 UPI。

假设：把内存搬到 GPU 同侧，跨片访存消失，均值和尾部一起降。

改动只有 PVE 三个字段：

改完回读：主内存 bind:0，16 GiB 全在 node0；QEMU、8 个 vCPU 和已采集的辅助线程 CPU 允许范围都在 node0 池内。

数据：改前改后各两个独立加载轮次，每轮预热 8 次、有效 64 次，合并 128 个样本。

条件 mean P50 P95 P99 max
改前（合并） 202.24 200.92 210.59 223.74 265.93
改后（合并） 193.08 192.26 199.84 215.76 253.10

mean -9.16 ms（4.53%），P95 -10.75 ms（5.10%），改后两轮都低于改前两轮。追加 256 次稳态复验：mean 190.67、P95 193.48。

结论：有效，但三条限制必须一起声明——P99 不能宣布收敛（改后仍有 253 ms 尖峰）；CPU 范围和内存本地性是一起改的，收益拆不开；带载采样 CPU 活动均频都在 2689–2692 MHz、GPU 温度功耗无系统差异，没有证据说明收益来自频率或配额节流，就是访存路径。

第二轮：固定物理核，没有收益

时间去向：第一轮之后 vCPU 在 node0 池内仍会迁移（30 秒采样约 85 次）。

假设：迁移本身有代价，把每个 vCPU 钉死到具体物理核，迁移归零，尾延迟应该进一步降。

结果：同一 QEMU 下 CPU 池与固定核交替四轮，固定核 mean 慢 0.60 ms（0.31%）、P95 慢 0.72 ms；只有 P99 低 15.46 ms、max 低 66.75 ms，样本量不足以支撑尾延迟结论。迁移次数按预期归零（对照组 81/80 次），但均值和 P95 没换来任何东西。

结论：回滚，没有固化。这轮的价值在决策：一个指标（迁移次数）降了，不代表延迟降了；不把它回滚掉，第三轮的变更里就会混进绑核变量。顺带澄清一个常被夸大的说法：来宾里 taskset -c 0-7 只约束这 8 个 vCPU，不证明独占物理核，不证明固定，也不证明没和其他 VM 共享 SMT 兄弟核。isolcpus、nohz_full、GPU 中断亲和都没做，属于未验证区域。

第三轮：普通 24Q 换 MIG 硬分区，收益最大

时间去向：四台共享一张卡，普通 24Q 四路并发 mean 204.4–204.8 ms（每台 508–510 个共窗样本），尾部抖动明显。多出来的时间在哪？四个 24Q 的显存和算力加起来就是一整张卡，四台同时提交时，时间片调度下每个实例的 kernel 要等前一个让出，排队堆在均值和尾部上。

假设：硬分区，46 SM 独占，没有队列，四路并发能降到单实例计算水平加固定开销。

改动：模型、权重、输入、线程契约全部冻结，换的只有切分方式——DC-24Q 换成 DC-1-24Q。

数据，两种工况分开测（单位 ms）：

工况 n/台 mean P95 max
四路连续调用 1024 114.7–115.9 116.9–118.9 125.5–136.9
每 640 ms 四路同步发起 768 120.4–126.9 125.8–148.2 176.6–193.2

204 → 115 ms。这就是 MIG 在这里的价值：并发负载下把时间片排队整个消掉。注意边界——单实例场景 24Q 和 MIG 24Q 没有本质差别，MIG 是四路并发场景的解法，不是让单实例变快。

640 ms 同步发起这组还留了个 NUMA 反例，我起初读反了，对着逐台数据重算才发现方向。四台分两类：605/606 的 CPU 池在 node1（与 GPU7 同侧），内存跨节点交错；607/608 在 node0（跨节点访卡），内存 bind 在 node0。实测均值 607 120.4、606 121.2、605 121.3、608 126.9 ms。跨节点组均值确实高 2.4 ms，但同一绑法内部差 6.5 ms，比两组间差距大一倍多，且最快最慢都出自跨节点组。信号方向一致、量级不可信，只记到此为止。同日 2048 样本复验排序一致：607 最快 119.75、608 最慢 122.86，四台全部低于 200 ms。所以第一轮”内存搬到 GPU 同侧更快”在这批数据上没有被干净复现。

代价：换 MIG 后原始动作张量在可比点上的最大绝对差 0.015625。这个量级算不算可接受的物理控制误差，由研发按实际控制量和轨迹容差判，我们只报数不替签。

抓球模型：同一布局的另一组数

同一个 MIG 布局，换成抓球模型（四摄像头、无 CUDA Graph）按 640 ms 节拍提交，四路并发 3760 次节拍调用超过 640 ms 的 0 次；mean 206.5–210.4 ms、max 287.6–307.8 ms；连续 300 秒口径 mean 199.9–203.0 ms（9710 次有效调用）。

这组数跟普通 24Q 的 204 ms 挨在一起纯属巧合，不是同一套模型，不能当 MIG 的对照基线。它真正说明的是模型侧的差距：没有 CUDA Graph 的模型在同一硬件布局上贵了将近一倍。

思路小结

三轮下来，比参数更值得带走的是方法：

  • **先找时间去向，再动手。**第三轮的前提是”四路 204 ms 与单实例 115 ms 的差距只能由时间片排队解释”，不是”MIG 新所以用”；
  • **尽量一轮一变，做不到就声明。**第一轮 CPU 范围和内存本地性一起改，第三轮换切分又动了内存策略，这两轮的收益到今天都没拆干净；
  • **没收益也是结论。**第二轮当场回滚，不然第三轮变更里会混进绑核变量；
  • **价值的边界是并发场景。**MIG 对四路并发值，对单机单实例是否值另说，不外推；
  • **模型层不是全链路。**这些毫秒都是离线模型层的数，上真机还要单独测采集、RPC 和派发。

ZFS M7 的逻辑额度治理只做了一部分；Pro6000 两个单盘池无副本，坏盘恢复未演练
高可用 双节点 quorate，无独立 QDevice、无 fencing 演练，两节点全挂即全停
在线迁移 测试机双向成功，有约 4 秒收包空档；带 vGPU/直通的迁移边界未验
备份 每日 NAS 作业按清单排除了全部边缘推理机和大模型机，实际只覆盖一台；生产机恢复未演练
vGPU MIG 冷启动持久性未验（钩子只核了文件摘要，未执行冷启动）；MIG 组合不在官方支持矩阵
推理 真机端到端延迟未测；608 的 193 ms 尾点未归因；动作容差待研发验收
硬件 一处网卡驱动软件补丁，器件级根因未定位；两次宕机现象相似，根因未定；450W 功率墙与调频迟滞疑似共振，机制未证明

小结

  • “还剩多少空间”先问是哪个口径：物理写入、可分配额度、声明容量、快照与预留是四个不同的数；
  • “bond 存在”不是冗余，”备份有文件”不是可恢复，”虚拟机 running”不是业务正常，每一句都要往前多走一步找判据；
  • 优化要有反例：绑核那轮明确没赢，写出来比只写 NUMA 那轮有用；
  • 解释不了的数据就标解释不了：第三轮我差点把四台均值差写成第一轮结论的延续，对着逐台数据重算才发现归因方向是反的——先有结论再找证据，比没有结论更容易出错。

把这套配置搬到别的负载之前，先按自己的并发、输入形状和节拍重测一遍。
