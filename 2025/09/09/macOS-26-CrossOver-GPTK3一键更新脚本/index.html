CrossOver Preview 与 GPTK 3 Beta 的更新试验

发表于2025-09-09|更新于2026-11-23|系统运维游戏优化
|总字数:1.1k|阅读时长:3分钟|浏览量:

2025 年 9 月用 macOS 26 测试版、CrossOver Preview 和 GPTK 3.0 beta 3 试 Windows 游戏。那时写了个脚本换组件，一处在应用包里，另一处在用户容器里。失败以后，两处留下的东西不一定相同。

下面说的都是那一版组合。受管终端和其他版本没跑过，后面换版本时要再查安装结构、授权和签名要求。Apple Game Porting Toolkit

当时为什么写脚本

手工操作分散在应用包及用户容器两处。应用包里的组件影响该安装实例，容器可理解为独立的 Windows 环境，里面有自己的一套文件和设置。只记录“升级了 GPTK”容易忘记动过哪一层。我的脚本把发现评估环境、备份旧目录、复制、检查，以及后续容器选择，每一步都留一行记录。核心目录用时间戳关联到同一次操作，容器修改留在用户选中的范围。

脚本会根据卷名前缀和预期目录寻找评估环境，也会探测目标位置是否存在及可写。卷名匹配只帮它找到输入，证明不了版本就是 beta 3，也证明不了来源。哪些库能配合工作，得看软件版本、文件清单和实际启动结果。那轮实验是固定组合的预研，误选新版的可能没堵死。

代码如何区分几类失败

原实现的核心过程简化成下面这段状态记录，只用来解释现场，实际文件操作略过。

故障点 当时的代码行为 停下时应如何理解
第二个旧目录改名失败 第一个目录已经处理就不会自动撤回 可能出现部分备份，两个目录的改名不是一次原子操作
复制报错或目标目录缺失 走恢复分支，尝试将时间戳备份移回 只能说明发起过恢复。若目标已部分存在，目录移动的结果仍需逐项核对
复制后摘要不一致 汇总失败数并询问是否继续 即使选择退出，新文件也可能留在应用包，脚本没有自动回滚
找不到摘要工具 警告并跳过校验 流程即使走到结尾，也没有完整性证据
后段图形组件改名失败 退出 先前已成功的步骤可能保留，后段也未采用整轮事务

当时的 MD5 比对针对 DLL、SO 和 dylib 一类文件，用于发现两份副本的意外差异。它只比对内容，管不到许可、权限、签名和嵌套代码完整性，镜像可不可信要另验。容器里的文件变更另有影响范围。旧版本还会在选目录时遇到不同位置的同名容器，仅凭显示名不够识别目标。

我现在会怎么设计这类更新

当时把每个操作写进日志，已经能区分“哪一步失败”和“恢复有没有被触发”。但把两个目录逐个改名后再往应用包复制，不能承诺失败后还能直接启动。换成今天的设计，我会先认清支持的源版本和目标版本，再在独立暂存位置核对完整文件清单、权限和签名状态。切换动作要有清晰的恢复点。发布前通过更换前后读回、冷启动和最小功能测试确认，发生失败时还要能让原版本真正工作。

交给别人复查时，我会先给他看输入版本和备份里到底有什么，再看失败停在哪，以及恢复后能不能冷启动。Gatekeeper 和受管终端下的表现这次没测。
